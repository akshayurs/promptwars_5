# EventCraft

Live: https://eventcraft-lac.vercel.app

EventCraft is a planning assistant for weddings, birthdays and community events. You describe the event (type and type-specific details, name, date, guest count, budget, currency, location, vibe and must-haves) and Gemini 2.5 Flash returns a structured plan: a budget breakdown, a dated timeline of checkable milestones, a vendor checklist with questions to ask, and ideas that cite which part of your brief inspired them. You can edit budget lines and the total, tick milestones and vendors off, ask the model to revise the plan in natural language (with one-step undo), change the event details and have the plan adapted to them, cancel a slow request, and export the result as JSON (re-importable), a calendar (.ics) or a budget CSV, or print it. The Gemini key is only ever used on the server; the plan itself lives in your browser's localStorage.

## Features

- Intake form with type-specific fields: couple names and ceremony style (wedding), guest of honour and age (birthday), admission type and permit need (community).
- Budget table with editable amounts and total (out-of-range values are flagged inline, not clamped), add and remove lines with an Undo for the last removal, and a live allocated-versus-total status with an over-budget warning.
- Timeline in date order, grouped by phase (phases only move forward), with real dates, completion checkboxes, progress, "Overdue" and "Due this week" badges, and a "Next up" card.
- Vendor checklist with why-needed, questions to ask, a booked checkbox and progress. Each vendor names the budget line it serves; if supplier budget lines have no vendor the server asks the model once more.
- Ideas that each name the intake detail that inspired them.
- Refine panel: a free-text instruction revises the whole plan; booked vendors and completed milestones are carried over; one-step undo.
- Edit event details (`/plan/edit`): change any intake field, including the total budget, guest count and date, and Gemini adapts the plan to the new details through the refine endpoint; completed milestones and booked vendors carry over where they still apply. The previous plan is not kept for undo.
- Cancel button while a plan is generating, being refined or being adapted; the typed answers are kept. Starting a new plan asks for confirmation before it replaces the plan saved in the browser.
- Printable summary; JSON, calendar (.ics, an all-day entry for the event and for every milestone) and budget CSV downloads; import of an exported plan from the intake page (choose a file, then select Import plan; it is validated against the 262,144 byte limit and confirmed before it replaces a saved plan). A visible alert appears if the browser cannot save changes and start over.

## Architecture

```
Browser (IntakeForm / RefinePanel)
  | IntakeSchema.safeParse on the client (fast feedback)
  | fetch POST /api/plan or /api/refine  (lib/client.ts)
  v
Route handler (app/api/plan/route.ts, app/api/refine/route.ts)
  -> createPlanRoute (lib/api/planRoute.ts)
       1. cross-site check (Sec-Fetch-Site, else full Origin)   (lib/http.ts)
       2. in-memory token-bucket rate limit per client key   (lib/rateLimit.ts)
       3. content-type, 131,072 byte body limit, JSON parse  (lib/http.ts)
       4. Zod validation of the request body                 (lib/schema.ts)
       5. in-flight cap: 2 running generations per client    (lib/concurrencyLimit.ts)
       6. 45 s timeout combined with the request abort signal
  v
Gemini 2.5 Flash, structured JSON output (lib/gemini.ts)
  responseMimeType application/json + JSON schema derived from the Zod schema
  (constraint keywords stripped, lib/geminiSchema.ts), prompts built in lib/prompts.ts,
  temperature 0.7 for generate and 0.3 for refine, one retry only if the output is malformed
  v
Zod parsing of the model output (LenientGeneratedPlanSchema, lib/generatedPlanSchema.ts):
  over-long text and lists are truncated, missing or empty required content is rejected
  v
Server rules and ids (fitPlanToIntake, toPlan / mergeRefinedPlan in lib/plan.ts)
  v
Browser validates the response again (PlanSchema in lib/client.ts)
  v
Client store (lib/workspaceStore.ts + lib/workspace.ts reducer, read through useSyncExternalStore)
  v
localStorage key "eventcraft.plan.v2" (lib/storage.ts, validated with StoredWorkspaceSchema on read)
```

Failures map to HTTP status codes, checked in this order: 403 cross-site request, 429 rate limited (with `Retry-After`), 415 wrong content type, 413 body too large, 400 invalid JSON or failed validation, then 429 again when the client already has 2 generations running (`Retry-After: 10`), then from the model call 200 success, 499 client closed the request, 502 upstream failure or malformed model output, 503 model busy (with `Retry-After`), 504 timeout, 500 unexpected. Every response carries `X-Request-Id` (and `correlationId` in error bodies), `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and a locked-down `Content-Security-Policy`; responses after the cross-site check also carry `RateLimit-Policy` and `RateLimit` ([lib/api/responses.ts](lib/api/responses.ts)). `/api/csp-report` uses the same helpers and answers 204, 400, 413, 415 or 429. Rejections log only status and reason, never the body.

## Security notes

- **Server-only key**: `GEMINI_API_KEY` is read in [lib/env.ts](lib/env.ts) and used only in [lib/api/deps.ts](lib/api/deps.ts) and [lib/gemini.ts](lib/gemini.ts) inside route handlers. It is not exposed through a `NEXT_PUBLIC_` variable.
- **Env validation at startup**: [instrumentation.ts](instrumentation.ts) calls `readEnv()` when the Node.js runtime registers, so a missing key fails fast.
- **Strict Zod at every boundary**: request bodies (`IntakeSchema`, `RefineRequestSchema`), model output (`LenientGeneratedPlanSchema`, server-only, which truncates over-long text and lists to the limits instead of rejecting them), the API response as read by the browser (`PlanSchema`) and the stored workspace (`StoredWorkspaceSchema`). The intake, refine request, plan and workspace schemas are strict (unknown keys are rejected) and text fields have length limits ([lib/constants.ts](lib/constants.ts) `LIMITS`).
- **Body size limit**: 131,072 bytes (`LIMITS.requestBodyBytes`), checked against `Content-Length` and again while streaming the body ([lib/http.ts](lib/http.ts)); non-JSON content types get 415 and invalid UTF-8 or JSON gets 400. CSP reports are capped at 8,192 bytes.
- **Cross-site protection**: the API route handlers answer 403 to browser requests sent from other sites (`Sec-Fetch-Site` other than `same-origin` or `none`; without it, an `Origin` whose full origin differs from the public origin of the request), so third-party pages cannot spend the model quota through a visitor's browser ([lib/http.ts](lib/http.ts)).
- **Rate limiting**: token bucket per client key (capacity 10, refill 0.2 per second) in [lib/rateLimit.ts](lib/rateLimit.ts); 429 with `Retry-After`, and `RateLimit-Policy` and `RateLimit` headers on the other responses ([lib/api/responses.ts](lib/api/responses.ts)). The key is the right-most `x-forwarded-for` hop (appended by the platform proxy), falling back to `x-real-ip` ([lib/http.ts](lib/http.ts)); IPv6 addresses are keyed by their /64 prefix and IPv4-mapped ones as IPv4 ([lib/clientAddress.ts](lib/clientAddress.ts)). Each client key may also have at most 2 generations running (`API.maxInFlightPerClient`, 429 with `Retry-After: 10`, [lib/concurrencyLimit.ts](lib/concurrencyLimit.ts)); the bucket map is capped at 10,000 keys with least-recently-used eviction.
- **CSP with a per-request nonce**: [proxy.ts](proxy.ts) builds `default-src 'self'`, a nonce plus `'strict-dynamic'` script policy, a nonce-based `style-src`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, `connect-src 'self'`, and `report-uri` / `report-to` pointing at `POST /api/csp-report` (`'unsafe-eval'` only in development). The report route is rate limited, size capped, and logs only counts of the violated directive and blocked host ([lib/api/cspReport.ts](lib/api/cspReport.ts)).
- **Security headers**: [next.config.ts](next.config.ts) sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security` (two years, `includeSubDomains`), `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, `X-Permitted-Cross-Domain-Policies`, and disables `X-Powered-By`. JSON responses from the API routes carry their own `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`.
- **Input hygiene**: control and bidirectional formatting characters are stripped from user text by the intake and refine schemas ([lib/sanitize.ts](lib/sanitize.ts)).
- **Model safety**: Gemini runs with explicit `BLOCK_MEDIUM_AND_ABOVE` safety settings for harassment, hate speech, sexually explicit and dangerous content; a blocked prompt or early stop is an upstream failure ([lib/gemini.ts](lib/gemini.ts), [lib/geminiResponse.ts](lib/geminiResponse.ts)). The system prompt tells the model to ignore text that asks for anything other than planning the event, and a refine request edited to move the event date outside the new-plan window is rejected by the server's schema.
- **Prompt-injection mitigation**: [lib/prompts.ts](lib/prompts.ts) wraps user input in `<intake>`, `<current_plan>`, `<keep>` and `<request>` tags (escaping `<` inside them) and tells the model to treat the tagged content as data, not instructions. Output is constrained by a JSON schema and re-validated, so injected text can at worst change plan content, not shape or behaviour.
- **Privacy notice**: the submit area tells the planner that the event details are sent to Google Gemini and that the plan is saved only in this browser ([components/intake/SubmitArea.tsx](components/intake/SubmitArea.tsx)); the intake page links back to a saved plan ([components/intake/ExistingPlanNotice.tsx](components/intake/ExistingPlanNotice.tsx)).
- **No HTML rendering of model output**: all model text is rendered as React text nodes; there is no `dangerouslySetInnerHTML`.
- **localStorage validated on read**: [lib/storage.ts](lib/storage.ts) parses with `StoredWorkspaceSchema` and removes the entry if it is corrupt or invalid.
- **Errors and logs**: upstream failures return generic messages; logs are JSON lines carrying a correlation id, status, reason code, model call duration and token counts, never request bodies, plans or prompts ([lib/logger.ts](lib/logger.ts)). [instrumentation.ts](instrumentation.ts) also logs unhandled request errors by digest, method and path, and the error pages show that digest as a reference id ([components/ui/ErrorReference.tsx](components/ui/ErrorReference.tsx)).

## Accessibility notes

Target: WCAG 2.2 AA, plus AAA where it is cheap (enhanced contrast preference, reduced motion). The technique-by-criterion table, with file references, is in [docs/ACCESSIBILITY.md](docs/ACCESSIBILITY.md).

- Landmarks: skip link, `header`, `nav` ("Primary"), `main#main`, `footer` in [app/layout.tsx](app/layout.tsx); `lang="en"` on the document. Nav links set `aria-current="page"`.
- Every route has its own document title (`Plan a new event`, `Workspace`, `Edit event details`, `Summary`, `Page not found`; the global error boundary sets `Something went wrong`), exactly one `h1`, and headings that do not skip levels. After a client-side route change the workspace, edit page and summary move focus to their `h1`; on a direct load or reload focus stays at the document start so the skip link remains the first Tab stop ([components/useHeadingFocus.ts](components/useHeadingFocus.ts)). Page titles and the navigation labels come from `PAGE_TITLES` in [lib/messages.ts](lib/messages.ts).
- Every control is labelled; hints and errors are wired with `aria-describedby` and `aria-invalid` ([components/ui/Field.tsx](components/ui/Field.tsx)). The intake form states that all fields are required unless marked optional. After a failed submit, focus moves to an error summary at the top of the form that links to each invalid field in form order; following a link focuses the field ([components/intake/ErrorSummary.tsx](components/intake/ErrorSummary.tsx)).
- Long requests (plan generation and refinement, typically 20 to 40 s): the form carries `aria-busy` while pending, the busy button stays focusable with `aria-disabled`, and a polite status region outside the busy form announces progress. If the request is still running after `LONG_WAIT_NOTICE_MS` ([lib/constants.ts](lib/constants.ts), 10 s), the status adds a reassurance that generation usually takes about half a minute ([components/usePendingRequest.ts](components/usePendingRequest.ts)); the timer is cleared on completion and unmount.
- Cancel: while a request is pending a Cancel button appears next to the progress status; cancelling announces "Plan generation cancelled" (or the refine or update equivalent) and returns focus to the submit button (intake) or the refine status region ([components/usePendingRequest.ts](components/usePendingRequest.ts), [components/IntakeForm.tsx](components/IntakeForm.tsx), [components/refine/useRefinement.ts](components/refine/useRefinement.ts)).
- Replacing a saved plan shows an inline `role="group"` confirmation that takes focus ([components/intake/ReplaceConfirm.tsx](components/intake/ReplaceConfirm.tsx)); the import file input has a label, a hint and an `aria-invalid` error announced with `role="alert"` ([components/intake/ImportPlan.tsx](components/intake/ImportPlan.tsx)).
- Budget amount and total inputs show an out-of-range value as an `aria-invalid` field with a linked message stating the allowed range instead of clamping it ([components/budget/useAmountDraft.ts](components/budget/useAmountDraft.ts)); removing a budget line is announced ("Removed <category>.") and focus moves to the add button.
- Disabled controls always come with a text reason: the minimum and maximum budget lines, and "Nothing to undo yet." next to the disabled undo button (linked with `aria-describedby`).
- Status messages use `role="status"` (vendor and milestone progress, budget status, refine result, loading); dates are marked up with `<time dateTime>`.
- Tabs and checkboxes use Radix primitives, which provide arrow-key navigation and correct ARIA roles; tables have captions and header scopes.
- Target size (2.5.8): buttons, tabs, nav links and form controls are at least 44 px tall (`min-h-11`), checkboxes are 24 px, error summary links are at least 24 px tall, and the native radios sit inside full-row labels at least 44 px tall.
- Focus not obscured (2.4.11): the header is sticky only on viewports at least 40rem wide and 32rem tall (a Tailwind `sticky-header` variant), and the same media query sets `scroll-padding-top: 6rem`, more than the header height, so focused elements scroll clear of it. On phones and short or zoomed windows the header scrolls away.
- Reflow and text spacing (1.4.10, 1.4.12): layouts are single-column at 320 px, the tab list wraps instead of overflowing, the budget table hides its rationale column into the category cell on phones, and text containers use minimum heights rather than fixed heights.
- Contrast: every text pair meets 4.5:1 and control borders, focus rings and progress fills meet 3:1 in light and dark schemes. `prefers-contrast: more` darkens secondary text and strengthens borders.
- Forced colours (Windows High Contrast): [app/globals.css](app/globals.css) maps focus rings to `Highlight`, keeps the selected tab underline, checked checkboxes, the selected event type, progress bars and the current nav link visible with system colours, gives background-only buttons and badges a border, and shows disabled controls in `GrayText`.
- Reduced motion: `prefers-reduced-motion` stops transitions, animations (including the spinner and loading skeleton, which also use `motion-reduce:animate-none`) and smooth scrolling.
- Redundant entry (3.3.7): a failed generation keeps everything typed, switching event type keeps the details already entered for each type, and the workspace pre-fills the total budget from the intake.
- State is never conveyed by colour alone (icons and text accompany alert tones and badges). A dark colour scheme is provided.

Keyboard-only walkthrough, done by hand on a production build in Chrome (2026-10-28):

1. The first Tab focuses "Skip to main content"; Enter moves focus to `main`.
2. Tab reaches the event-type radio group; arrow keys switch the type and the matching detail fields appear in place.
3. Tab then visits every field in visual order (name, type-specific details, date, guests, budget, currency, location, vibe, must-haves) and ends on "Generate plan"; each control shows the focus ring.
4. Submitting with empty fields moves focus to the error summary, which is scrolled into view, and marks each invalid field with `aria-invalid`.
5. In the workspace, arrow keys move between the Budget, Timeline, Vendors and Ideas tabs, and Space toggles milestone and vendor checkboxes.

The Playwright suite automates only part of this, on desktop and mobile viewports: step 1 (Tab then Enter), step 4 (focus on the error summary and `aria-invalid` on the invalid fields) and, in step 5, the ArrowRight tab switch and Space on a milestone and a vendor checkbox. Steps 2 and 3 (radio arrow keys and the full tab order) are manual checks only; see the checklist in [docs/ACCESSIBILITY.md](docs/ACCESSIBILITY.md).

## Efficiency notes

- Server components by default. Every module that uses React hooks, defines event handlers or uses `next/navigation` or `next/dynamic` starts with `"use client"`: the intake form and its fields, import control and edit page, workspace and its tabs, budget table and rows, timeline and milestones, next-up card, ideas list, vendor checklist, refine panel, summary page and actions, active nav link and the error boundaries. Presentational modules without them (alerts, icons, form fields, skeletons, the budget grid) carry no directive and render inside those boundaries.
- One model call per user action (generate or refine); a second call happens only if the first response fails schema validation (`API.geminiMalformedRetries` in [lib/constants.ts](lib/constants.ts), used by [lib/gemini.ts](lib/gemini.ts)).
- Bounded cost: `maxOutputTokens` 16,384, thinking budget 512, request timeout 45 s, temperature 0.7 (generate) and 0.3 (refine), and list size caps in the schema; all from `API` and `LIMITS` in [lib/constants.ts](lib/constants.ts).
- The refine panel and the checkbox primitive are loaded with `next/dynamic` ([components/PlanWorkspace.tsx](components/PlanWorkspace.tsx), [components/ui/CheckControl.tsx](components/ui/CheckControl.tsx)), so the read-only summary never downloads the checkbox code.
- State lives in a small external store read with `useSyncExternalStore`; persistence is one localStorage write per change, except that per-keystroke budget edits (`setAmount`, `setTotalBudget`) are coalesced for `PERSIST_DEBOUNCE_MS` (300 ms) and flushed when the page is hidden or unloaded.
- Client JavaScript for all routes totals 241 KiB gzipped (17 chunks, measured from `.next/static` after `next build`). The Gemini SDK and the API key never reach the browser: the server-only modules import `server-only`, and a scan of the built chunks finds no `@google/genai` or `GEMINI_API_KEY`.
- In the browser Zod runs in `jitless` mode ([lib/zod.ts](lib/zod.ts)) so its `new Function` capability probe never trips the nonce CSP; the server keeps Zod's compiled parsers.

## Deployment

The app is hosted on Vercel at https://eventcraft-lac.vercel.app.

- `GEMINI_API_KEY` is configured as a sensitive Production environment variable in the Vercel project; it is never committed.
- Serverless functions run in the Mumbai region (`bom1`, [vercel.json](vercel.json)), close to the INR-first audience.
- The GitHub repository is connected to the Vercel project: every push to `main` deploys to production, and every other branch gets a preview deployment.
- CI in [.github/workflows/ci.yml](.github/workflows/ci.yml) runs on every push and pull request with two jobs. `verify` runs `npm audit --omit=dev --audit-level=moderate`, lint, formatting, type check, unit tests with coverage (uploaded as an artifact), knip and the production build. `e2e` runs the Playwright end-to-end and accessibility suite on desktop and mobile projects and uploads the report on failure. Actions are pinned to commit SHAs and the workflow token is read-only.
- Security workflows: [CodeQL](.github/workflows/codeql.yml) analyses JavaScript and TypeScript on pushes and pull requests to `main` and weekly; [dependency review](.github/workflows/dependency-review.yml) fails pull requests that add dependencies with moderate or higher vulnerabilities, and CI runs `npm audit --omit=dev --audit-level=moderate`; [secret scanning](.github/workflows/security.yml) runs Gitleaks on pushes, pull requests and weekly. [Dependabot](.github/dependabot.yml) opens weekly grouped updates for npm packages and GitHub Actions.

## Known limitations

- The rate limiter is in memory, so each server instance has its own counters and they reset on restart. On Vercel, each serverless instance keeps separate counters, so the effective limit is per instance rather than global. A shared store (for example Redis) would be needed for a global limit.
- Plans are stored only in the browser's localStorage: no accounts, no sync across devices, cleared with site data. One plan at a time and one level of undo.
- The UI is English only, and currency and date formatting use fixed locales per currency.
- `npm audit` and `npm audit --omit=dev` both report 0 vulnerabilities, checked on 2026-10-28.
